# OEM 全家桶识别与安全清理设计

## 状态与范围

- 设计日期：2026-08-11
- 目标平台：Windows PowerShell/WPF 桌面应用
- 功能基线：`b31d631`
- 适用规则格式：profile Schema 3.0
- 适用待执行格式：pending Schema 2
- 范围：让现有扫描、规则匹配、复核、提权执行、备份、验证和恢复链路在真实规则数据上可达，并补齐可疑后台的安全处置入口

本设计不通过放宽授权闸门来增加“可清理数量”。它修正规则数据与匹配选择，使经过实机验证的稳定标识能够生成安全动作，同时继续把宽匹配、未实测 OEM 和无法证明身份的后台进程限制为观察项。

## 目标

软件必须真实完成以下任务：

1. 扫描服务、启动项、计划任务和进程，识别 OEM 全家桶及可疑后台。
2. 清楚区分“发现了”与“允许处理”。
3. 对已实测、标识稳定、实际由 `exact`/`path` 命中的 OEM 项目提供安全处理。
4. 对 `contains`/`regex`、未实测规则和未知身份只提供观察或一次性进程终止，不授予持久化系统修改权限。
5. 每个持久化修改都经过备份、管理员权限下的同证据复核、执行后回读验证，并可恢复。
6. GUI 准确反映可执行性；没有已选择的合格动作时，执行按钮必须禁用。

## 已确认的安全不变量

1. **识别可以宽，执行必须窄。** 只有本次实际命中的 matcher 为 `exact` 或 `path` 时，危险动作才可能进入执行队列。
2. **实际命中证据决定授权。** 同一 profile 中存在其他窄 matcher，不能把一次 `contains`/`regex` 命中升级为可执行动作。
3. **`allow_auto` 不是安全绕过。** 该字段只保留兼容和审计意义，不能扩大执行授权。
4. **实测证据是必要条件。** `safe=true` 且 `evidence.tested=true` 才能生成持久化清理动作。
5. **提权后重新证明。** 管理员进程必须用 pending 中相同的 pattern、type、field 和当前目标身份再次验证。
6. **失败关闭。** 数据缺失、目标变化、规则变化、扫描不完整、备份失败或回读不一致时，跳过该项，不猜测、不降级执行。
7. **用户选择不是授权证明。** GUI 勾选只表达用户意图，不能替代核心层复核。

## 方案选择

采用“校准真实规则数据并保留现有安全闸门”的方案。

未采用的方案：

- 不恢复 `allow_auto` 对宽 matcher 的豁免，因为它会重新引入 Schema 3.0 的授权扩张漏洞。
- 不把所有 OEM 关键词机械改成 `exact`，因为进程显示名、启动项文本和不同机型上的名称可能不稳定。
- 不提供“强制清理 contains/regex 命中”的高级开关，因为它会让 UI 绕过核心安全模型。

## 架构边界

### 1. 采集层

继续采集四类对象：

- 服务：内部服务名和显示名；
- 启动项：受支持 Run 键中的值名、值内容和来源；
- 计划任务：任务名和完整任务路径；
- 进程：PID、进程名、可执行路径，以及可获得时的启动时间。

每个采集器必须报告 `complete`、`degraded` 或 `failed`。采集不完整时，UI 可以展示已经获得的观察结果，但不得宣称整机干净；依赖缺失采集类别的动作不得进入执行队列。

### 2. 规则层

规则按证据强度分成两组：

- **可执行规则**：仅限已经实机验证且具有稳定身份的 `exact`/`path` matcher。
- **观察规则**：`contains`、`regex`、未实测厂商规则、通用关键词和不稳定进程名称。

首批可执行规则只覆盖当前已经记录为 `evidence.tested=true`、并能从实机采集结果确认稳定内部名称或完整路径的联想项目。Dell、ASUS、HP、Huawei、Xiaomi 和 Generic 中 `tested=false` 的项目继续只观察，直到获得独立实机证据后再通过单独变更升级。

服务优先使用 Windows 内部服务名的 `exact` matcher，不使用显示名关键词授权。计划任务使用规范化后的完整任务路径 `exact`。启动项只有在值名或规范化可执行路径稳定且经过验证时，才能使用 `exact`/`path`；否则保持观察。进程关键词继续用于识别，不授予服务、启动项或任务的持久化修改权限。

### 3. 匹配与命中选择层

每次 matcher 成功都生成候选证据：

```json
{
  "matched_pattern": "LeMCPManagerService",
  "matched_type": "exact",
  "matched_field": "service_name"
}
```

同一 profile、同一对象、同一命中类别可能被多个 matcher 命中。最终只产生一个面向用户的命中记录，并按以下优先级选择证据：

1. 实际成功的 `exact`；
2. 实际成功的 `path`；
3. 实际成功的 `contains`；
4. 实际成功的 `regex`；
5. 其他仅检测类型。

该优先级只在多个 matcher **确实都匹配同一个当前对象** 时选择更强证据，不允许借用未命中的窄 matcher。相同强度时保持规则文件中的声明顺序，以保证结果稳定。

选择后，命中记录必须保存 pattern、type 和 field。危险 action 只有在 `safe=true`、`evidence.tested=true` 且选中的实际 matcher 为 `exact/path` 时保留；其他情况统一降级为 `investigate` observation，并记录不可执行原因。

### 4. Pending 与执行层

扫描结果继续分成：

- `actions`：满足全部可执行条件的持久化动作；
- `observations`：宽匹配、未实测、不安全或不完整采集产生的只读结果；
- `suspicious`：资源占用或行为值得用户关注、但尚未绑定到可执行 OEM 规则的进程。

持久化动作的处理顺序固定为：

```text
用户选择
  -> 生成并哈希绑定最小 pending 子集
  -> 请求管理员权限
  -> 重新加载当前 profile
  -> 用同 pattern/type/field 复核当前身份
  -> 创建备份
  -> 执行动作
  -> 回读验证
  -> 写入逐项结果和恢复信息
```

各类型动作：

- 服务：备份启动类型和运行状态；停止并禁用；回读启动类型和状态；恢复时还原原启动类型，并按原状态决定是否重新启动。
- 启动项：备份注册表来源、值名、值类型和值数据；仅删除扫描器允许的 Run 键目标；回读确认；恢复时写回原类型和数据。
- 计划任务：备份完整任务路径及启用状态；仅禁用，不删除任务；回读确认；恢复时还原启用状态。
- 进程：OEM profile 的 `investigate` 命中不自动转成持久化动作；进程终止使用下述独立的一次性流程。

任何单项失败不得阻止其他已独立授权项目继续处理，但最终结果必须准确区分成功、失败和跳过，不能显示整体虚假成功。

## 可疑后台的一次性处置

可疑后台不是“恶意软件”结论。它只表示当前进程值得检查，例如资源占用异常、命中通用关键词或属于未验证 OEM 组件。

GUI 为可疑进程提供独立的“本次结束进程”操作，遵守以下限制：

1. 永不默认选中，用户必须明确逐项选择。
2. 不提供删除文件、卸载软件、删除启动项、禁用服务或创建永久黑名单。
3. 待处理记录绑定 PID、进程名、规范化可执行路径，以及可获得时的启动时间。
4. 执行前重新读取 PID；名称、路径或启动身份任一不一致即跳过，防止 PID 复用。
5. 系统关键进程、受保护进程、路径不可读进程和身份不完整进程不可操作，只显示解释。
6. 终止后回读确认进程已退出；失败时保留错误原因。
7. 若要进行持久化清理，必须通过已验证 OEM `exact/path` 规则形成独立 action，不能从 suspicious 列表直接升级。

## GUI 行为

现有“鼠鼠的幻想”单页状态旅程保持不变，功能层做以下补齐：

- Results 页分别显示“可安全处理”“仅供观察”“可疑后台”。
- Review 页只有 `actions` 中的项目可以勾选；observation 以禁用行展示具体原因。
- 已验证且满足全部条件的 OEM action 可按现有安全默认策略预选；可疑进程永不预选。
- `BtnExecute.IsEnabled` 仅在至少存在一个当前已勾选、仍可执行的 action 时为 `true`。
- 用户取消所有勾选、列表为空或只有 observation/suspicious 时，执行按钮立即禁用。
- 可疑进程的一次性终止使用独立按钮和确认文案，不与管理员持久化清理合并成一个模糊操作。
- 技术详情展示实际 matcher provenance、目标身份、证据状态、采集健康和不可执行原因。
- 扫描或执行结果为 partial/degraded 时，标题和摘要必须明确指出信息不完整。

## 错误处理

- profile JSON、pending JSON 或 matcher 证据无效：拒绝动作并提示重新扫描。
- 管理员子进程退出码非零、输出不可解析或结果文件不完整：显示执行失败，不合并为成功。
- 扫描类别 degraded/failed：保留诊断和已知观察结果，禁止依赖该类别的动作。
- 备份失败：不得执行对应修改。
- 修改后回读不符合预期：标记失败，保留备份并提示恢复；不伪造成功。
- 目标在扫描后消失或身份变化：标记 skipped，不对替代对象执行。
- GUI 资源或鼠鼠图片缺失：核心文字、选择、安全说明和操作仍可使用。

## 测试策略

实现采用红—绿—重构，每项生产变更先有失败测试。自动测试不得修改真实服务、Run 键、计划任务或生产进程。

### 规则和匹配测试

1. 当前真实 profile 集成测试证明已验证的稳定联想服务使用 `exact` 并生成 action。
2. 相似名称，例如 `LeMCPManagerServiceFake`，只能由宽 matcher 识别并进入 observation。
3. 同一对象同时命中 exact 和 contains 时，只产生一个记录，保存实际成功的 exact 证据。
4. 只有 contains 命中时，即使 profile 还声明未命中的 exact，也不能生成 action。
5. 未实测 OEM 即使使用 exact 也只能观察。
6. 计划任务完整路径和受支持启动项身份按各自字段精确匹配。

### 授权、备份和恢复测试

1. pattern、type、field、profile、action 或目标身份被篡改时，管理员复核失败且零修改。
2. 服务、启动项、任务的备份内容完整，执行后回读正确，恢复后回到原状态。
3. 备份失败、对象消失、对象替换和回读失败均按单项 fail-closed 处理。
4. pending 子集的哈希和锁定机制继续覆盖完整执行证据。

### 可疑进程测试

1. 没有明确选择时不终止任何进程。
2. PID 被复用、路径变化、启动时间变化、关键进程或身份不完整时拒绝终止。
3. 身份一致的受控测试进程可被一次性终止，并回读确认。
4. suspicious 记录不能生成服务、任务、启动项或卸载动作。

### GUI 测试

1. 只有 observation 时，所有行不可勾选且执行按钮禁用。
2. action 未选择时执行按钮禁用；选择后启用；取消后再次禁用。
3. action、observation 和 suspicious 的计数、文案和详情与 pending 一致。
4. partial/degraded 扫描不得显示“全部正常”或完整成功。
5. 受控端到端流程从真实按钮点击走通扫描、复核、模拟执行结果和恢复展示。

## 真实运行验收

自动测试全部通过后，进行分层验收：

1. 运行 AST、JSON、完整 Pester、旧逻辑和 Schema 回归，并执行 `git diff --check`。
2. 在当前机器进行真实只读扫描，确认中文输出、采集健康、OEM 命中分类和 pending 内容。
3. 启动真实 GUI，通过按钮完成扫描到 Review，确认窗口响应、计数、禁用状态和技术详情。
4. 使用受控夹具或专门创建的测试对象验证备份、清理、回读和恢复，不触碰真实 OEM 服务。
5. 对真实 OEM 项目，只展示为可选候选；是否执行真实禁用必须由用户在 GUI 中明确确认，不作为自动验收步骤。

## 非目标

- 不自动卸载 OEM 软件。
- 不删除服务或计划任务定义。
- 不根据“可疑”标签删除文件或做永久系统修改。
- 不在本阶段把所有品牌规则升级为可执行。
- 不弱化 Schema 3.0 matcher provenance、pending v2、哈希绑定或提权复核。
- 不因单元测试通过就直接合并或推送；必须完成真实 GUI 和受控端到端验收。

## 完成标准

只有同时满足以下条件才可判断实现完成：

- 已实测且稳定的 OEM exact/path 规则能在真实扫描链路中生成可选 action；
- 宽匹配、未实测规则和相似名称不会获得持久化执行权限；
- action 能在受控对象上完成备份、提权复核、修改、回读和恢复；
- 可疑后台只能经过明确选择和身份复核做一次性终止；
- GUI 在无合格选择时禁用执行按钮，并准确展示 action、observation、suspicious 和 partial 状态；
- 完整自动回归、真实只读扫描、真实 GUI 流程和受控变更/恢复验收均有最新通过证据；
- 合并和推送在上述证据审查通过后另行决定。
